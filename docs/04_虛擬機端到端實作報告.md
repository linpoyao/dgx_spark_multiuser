## 1. 摘要

前一份報告證明的是「設定檔寫得對」，本報告要證明的是「服務跑起來後，行為真的如設計」。兩者的差別，正好就是本次新發現的兩個 bug 所在：它們在靜態驗證下都能通過，只有服務實際運作時才會顯現。

1. **`hub_ip = "0.0.0.0"` 讓 Hub 登入頁暴露在所有網卡的 `:8081`。** 任何人可以繞過 Cloudflare Access（第二因素），直接對 PAM 嘗試密碼。
2. **idle-culler 的權限範圍少了 `read:servers`。** 結果是閒置容器永遠不會被回收，而且完全不報錯。

兩者均已修正，並在虛擬機中重新驗證通過。

## 2. 虛擬機環境

| 項目 | 內容 |
|---|---|
| 虛擬機 | Firecracker microVM，1 vCPU、3 GB RAM、x86_64 |
| 作業系統 | Ubuntu 24.04（kernel 6.18） |
| 容器引擎 | Docker Engine 29.1.3（overlayfs、cgroup v1） |
| Hub 端 | JupyterHub 6.0.0、DockerSpawner 14.0.0、jupyterhub-idle-culler 2.0.0、configurable-http-proxy（npm） |
| 使用者映像 | `lab/singleuser-sandbox:2026.09` |
| 帳號 | poyao（admin）、alice（lung）、bob（prostate）、guest1（短期，限 cohort2018）、mallory（系統帳號，但不在白名單） |

### 2.1 使用者映像怎麼來的

虛擬機的網路無法連到 Docker Hub 與 NGC，因此：

1. 以 `debootstrap` 從 Ubuntu 官方套件庫（archive.ubuntu.com）建出一份 Ubuntu 24.04 rootfs。
2. 用 `docker import` 匯入成 base image。
3. 在上面安裝 `jupyterhub==6.0.0`、jupyterlab、numpy、pydicom。

這個映像在功能上對應真機的 `lab/pytorch-arm64`，也就是提供 `jupyterhub-singleuser`。差別只在沒有 CUDA／PyTorch。

### 2.2 設定原則：覆寫層只動沙盒做不到的部分

`vm/jupyterhub_config_vm.py` 先 `exec` 載入**真機用的原版** `jupyterhub_config.py`，再只覆寫以下四項：

| 覆寫項目 | 原因 |
|---|---|
| 拿掉 `device_requests`（GPU） | 虛擬機沒有 GPU 與 nvidia runtime |
| `image` 改為沙盒映像 | 無法取得 NGC 映像 |
| `cpu_limit = 1`、`mem_limit = 1G` | Docker 會拒絕大於實體核心數的 CPU 限制 |
| culler `--timeout=90` | 讓閒置回收能在測試時間內被觀察到（真機為 4 小時） |

**安全相關設定一律沿用原版，覆寫層完全不碰。** 包括 PAM 驗證、白名單、掛載政策與 `pre_spawn_hook`、以本人 UID 執行、`cap_drop: ALL`、`no-new-privileges`，以及只綁 127.0.0.1。

## 3. 驗證方法

測試腳本是 `tests/e2e_vm.py`，以 root 執行。它模擬真實使用者走的路徑：

1. 以 `requests` 取得 `/hub/login` 的 XSRF cookie，POST 帳密登入。
2. 開 `/hub/spawn/<user>`，輪詢 `/user/<user>/lab`，直到頁面可開啟。
3. 用 `docker inspect` 檢查容器層級的設定。
4. 用 `docker exec` 在容器內執行指令。它沿用容器設定的 USER，所以身分就是該使用者本人。
5. 透過 proxy 呼叫 Jupyter Contents API，這是使用者在瀏覽器裡實際會走的路徑。

### 4.3 C. fail-closed（4/4）

測試做法：在執行中的 Hub 底下，把 `mount_policy.yaml` 的 `common` 注入一條「掛載 `/data/raw`」，然後讓 bob 登入並嘗試 spawn。

| 驗證 | 實測 |
|---|---|
| bob 的容器起不來 | spawn-pending 頁面回 HTTP 500 |
| 主機上沒有 `jupyter-bob` 容器 | 是 |
| Hub log 記錄了拒絕原因 | `掛載政策驗證失敗，拒絕為 bob 啟動容器：禁止掛載 /data/raw（落在拒絕清單 /data/raw 之下）` |
| 政策還原後，不必重啟 Hub 即恢復正常 | spawn 成功 |

這證明 fail-closed 在**真實的 spawn 流程**中有效，而不只是在單元測試裡有效。此外，因為政策檔是每次 spawn 時重新讀取，修正後不需要重啟 Hub。

### 4.4 D. 閒置回收（2/2）

alice 與 bob 各起一個容器後放置不動。**110 秒後兩者都被 idle-culler 回收**，容器也一併刪除（`DockerSpawner.remove = True`）。Hub log 的紀錄如下：

```
Culling server alice (inactive for 00:01:49)
Culling server bob (inactive for 00:01:45)
```

這個結果是修正 bug #2 之後才達成的，詳見 §5.2。

## 5. 新發現的問題

### 5.1 Bug #1：Hub API 綁在 0.0.0.0，可繞過 Cloudflare Access（安全性，高）

**現象**

原設定為 `c.JupyterHub.hub_ip = "0.0.0.0"`，本意是「讓容器連得到 Hub」。實測從主機的 LAN 位址存取：

```
via 127.0.0.1:8000（proxy）                          -> 200
via 192.0.2.2:8081（Hub 直連，繞過 proxy 與 Access）  -> 200
```

**影響**

在真機上，校內網路或 10GbE 網段上的任何人，都能直接開啟 `http://<Spark IP>:8081/hub/login` 並對 PAM 嘗試密碼：

- 完全不經過 Cloudflare Access 的 Google 登入，也就是第二因素。
- 雖然 fail2ban 在這條路徑上看得到真實 IP，但「第二因素可被繞過」本身就是設計上的破口。

**為什麼靜態驗證抓不到**

靜態測試檢查的是 `bind_url`（proxy 的對外埠 8000），它確實只綁 127.0.0.1。Hub API 自己的 8081 埠是另一個設定，只有服務實際監聽時用 `ss -tlnp` 才看得出來。

**修正**

- Hub API 只綁在 `jupyterhub-net` 的閘道上。
- 閘道位址改由 docker SDK 自動查詢，保留 `HUB_GW` 環境變數作為覆寫手段。
- 這同時消除了操作手冊 §7.2「手動查閘道再填入設定」的步驟。原本若漏做那一步，spawn 會卡在 timeout。

```python
def _docker_net_gateway(name="jupyterhub-net"):
    if os.environ.get("HUB_GW"):
        return os.environ["HUB_GW"]
    import docker  # dockerspawner 的相依套件
    return docker.from_env().networks.get(name).attrs["IPAM"]["Config"][0]["Gateway"]

c.JupyterHub.hub_ip = _docker_net_gateway()
c.JupyterHub.hub_connect_ip = c.JupyterHub.hub_ip
```

**修正後實測**

```
LISTEN 127.0.0.1:8000    (proxy)
LISTEN 127.0.0.1:8001    (proxy API)
LISTEN 172.18.0.1:8081   (Hub API，只在 docker bridge 上)
LAN 192.0.2.2:8081 -> 連線被拒
proxy 127.0.0.1:8000 -> 200
```

實測的閘道是 **172.18.0.1**，不是 docker0 的 172.17.0.1。這也印證了原設定中寫死 `hub_connect_ip = "172.17.0.1"` 在真機上會失效。

### 5.2 Bug #2：idle-culler 永遠不回收（維運，中）

**現象**

使用原設定時，四個容器閒置超過 8 分鐘（遠超過 90 秒的 timeout），都沒有被回收。culler 每 30 秒成功呼叫一次 `/hub/api/users`，但從未發出任何 DELETE。

**原因**

原設定給 culler 的 scopes 是 `list:users`、`read:users:activity`、`delete:servers`，**缺少 `read:servers`**。後果是一連串的：

1. Hub 回給 culler 的 user model 不含 `servers` 欄位。
2. culler 於是走進給 JupyterHub 0.8 用的相容分支，讀取 `user["server"]`。
3. 這個欄位也不存在，log 中出現 `KeyError: 'server'`。

整個過程對外完全沒有錯誤訊息，服務看起來一切正常，只是從來不回收。另外，原始規劃文件中的 `'admin': True` 寫法在 JupyterHub 2 以後已不再使用，照抄同樣不會生效。

**影響**

- 閒置容器永遠佔著記憶體。在 Spark 的統一記憶體架構下，這會直接壓縮其他人可用的訓練記憶體。
- `mem_limit 48G` 乘上幾個忘了關的容器，就足以讓別人的訓練 OOM。

**修正**

```python
"scopes": ["list:users", "read:users:activity", "read:servers", "delete:servers"],
```

修正後重啟 Hub，culler 在第一輪就回收了所有閒置伺服器，之後的乾淨重測也通過（§4.4）。

## 6. 順帶實證的事項

| 項目 | 結論 | 對文件的影響 |
|---|---|---|
| `jupyterhub-net` 的閘道 ≠ docker0 | 實測為 172.18.0.1 | 已改為自動查詢；手冊 §7.2 可刪除 |
| `passwd -l` 鎖住的帳號無法以 PAM 登入 Hub | 成立 | 手冊 §12.1 的說法正確，開帳號時必須解鎖 |
| 經 proxy 的失敗登入，來源 IP 為 127.0.0.1 | 成立 | 支持 `ignoreip` 的設計，proposal §9.2 正確 |
| `cleanup_servers = False` | Hub 重啟後使用者容器持續運作 | 升級或重啟 Hub 不會中斷訓練 |
| 停止使用者伺服器必須走 Hub API | 直接 `docker rm` 會讓 Hub 以為伺服器仍在，之後使用者會卡在 HTTP 424 | **需補進手冊 §12.4 與附錄 A** |
| JupyterHub ≥ 4.1 的 XSRF 規則 | single-user server 對 cookie 驗證的 API 請求一律要求 XSRF token，連 GET 也要 | 同學若寫腳本呼叫自己伺服器的 API，要先開頁面取得 `_xsrf`，或改用 API token |
| 政策檔每次 spawn 重讀 | 修改 `mount_policy.yaml` 不需重啟 Hub | 可寫進維運手冊 |

## 8. 本虛擬機無法驗證的項目

| 項目 | 原因 | 在哪裡驗證 |
|---|---|---|
| GPU 直通（`device_requests`）、`torch.cuda.is_available()` | 無 GPU 與 nvidia runtime | 真機驗收清單 #1 |
| arm64 映像建置（主映像、radiomics 映像） | 虛擬機為 x86_64，且無法連 NGC | 真機驗收清單 #2、#3 |
| MIG 不支援、統一記憶體上限攔不住 | 無 GB10 | 真機觀察 |
| Tailscale 與 Cloudflare Tunnel／Access 實際連線 | 無法安裝 client、沒有網域 | 真機驗收清單 #10、#11 |
| SSH 真實登入（公鑰可進、密碼與 guest 被拒） | 本輪未做（sshd 設定的靜態驗證已通過） | 下一輪可在虛擬機補做 |
| quota、auditd 實際生效 | 無 loop device、無 systemd | 真機驗收清單 #12、#13 |

若要在自己的電腦上重現，而電腦是 Apple Silicon 的 Mac，可以用 UTM 或 Multipass 開一台 Ubuntu 24.04 arm64 虛擬機。架構與 Spark 相同，因此能額外驗證 arm64 映像建置，只差 GPU。
