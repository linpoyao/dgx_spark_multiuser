## 1. 方法

不做「讀設定檔然後目視檢查」，而是讓每一條設計承諾都對應一條可執行的斷言：

| 驗證方式 | 用在哪裡 |
|---|---|
| `runuser -u <user>` 實際以各角色身分讀寫，逐條檢查 allow / deny | 帳號與資料樹權限 |
| 單元測試（正向 ＋ 負向攻擊向量） | 掛載政策 |
| traitlets 載入設定 ＋ 反射比對 trait 名稱 ＋ 以假 spawner 執行 hook | JupyterHub 設定 |
| `sshd -t`（語法）＋ `sshd -T -C user=...`（展開實際生效值） | sshd 硬化 |
| `fail2ban-client -d`（載入）＋ `fail2ban-regex`（比對樣本記錄） | fail2ban 與自訂 filter |
| YAML/JSON 解析 ＋ 跨檔交叉檢查 | cloudflared、Tailscale ACL、systemd unit |
| 查詢 PyPI 各套件實際檔案清單並判斷 wheel 相容性 | aarch64 套件盤點 |

**負向測試是重點。** 安全設定最危險的失效模式不是「報錯」，而是「靜靜地不生效」；只測正向路徑無法分辨這兩者。

## 3. 發現並修正的問題

### 3.1 `/data` 不可穿越，researcher 讀不到任何資料

第一次跑權限測試時 4 項 FAIL。原因是 `/data` 被設為 `0750 root:phi-raw`：`phi-raw` 以外的使用者沒有 `x` 權限，因此**連往下走到 `/data/deid` 都不行**，即使 `/data/deid/lung` 本身權限完全正確。

- 修正：`/data` 改 `0755 root:root`；存取控制放在下一層。
- 教訓：目錄權限要看「整條路徑」，不能只看目標資料夾。

### 3.2 `/data/raw` 設 `0700` 使 `phi-raw` 群組形同虛設

`0700 root:root` 之下只有 root 能讀，`phi-raw` 群組沒有意義，admin 每次都要 sudo。

- 修正：`2750 root:phi-raw`（setgid，匯入的原始檔自動屬 `phi-raw`），others 完全無權。

### 3.3 `/data/raw` 缺 default ACL，admin 匯入的檔案自己讀不到

修正 3.2 之後仍有 1 項 FAIL：目錄權限對了，但**檔案**是 `0640 root:root`，`phi-raw` 成員讀不到。

- 修正：`setfacl -m g:phi-raw:rx -d -m g:phi-raw:rx /data/raw`，並把「匯入一律 `0640 root:phi-raw`」寫進 ingest 規則。

### 3.4 `c.ConfigurableHTTPProxy.auth_token_file` 這個 trait 不存在

原規劃寫 `auth_token_file`，但 JupyterHub 6.0 的 `ConfigurableHTTPProxy` 只有 `auth_token`。traitlets 對不存在的 trait **不會報錯**，設定會被靜默忽略。

- 修正：改用 `auth_token = os.environ.get("CONFIGPROXY_AUTH_TOKEN")`，token 由 systemd 的 `EnvironmentFile`（`0600`）帶入，不進版控。
- 這是靠「反射比對 trait 名稱」抓到的，目視審閱不會發現。

### 3.5 fail2ban filter 的 failregex 永遠比對不到

原先 failregex 寫成 `^\s*\[[WEC] <日期> JupyterHub log:\d+\] 403 POST /hub/login...`，`fail2ban-regex` 結果是 **0 matched / 6 missed**。原因：fail2ban 會先用 `datepattern` 把行首日期**剝掉**才套 failregex。

- 修正：failregex 從 `JupyterHub log:` 開始。修正後 6 行樣本中正確抓到 3 筆失敗登入（含兩個不同來源 IP），且成功登入的 `302` 與 `200 GET` 不被誤判。
- 若沒測，這個 jail 會在「設定看起來完全正確」的狀態下完全不作用。

### 3.6 掛載驗證器把 `/` 當前綴比對，擋掉所有合法掛載

我在 deny 清單放了 `/`（用意是阻止 `-v /:/host`），但前綴比對之下「任何路徑都在 `/` 之下」，於是連 `/workspace/alice` 都被拒絕——fail-closed 設計會讓**沒有人能起容器**。

- 修正：`/` 只比對根目錄本身。
- 這正是負向測試的價值：政策「擋太多」和「擋太少」都是 bug。

## 4. 額外確認的兩個架構結論

### 4.1 fail2ban 對外網暴力登入無效，且會反傷

經 Cloudflare Tunnel 進來的請求，Hub 記錄到的來源 IP 一律是 `127.0.0.1`。若照一般作法啟用 jupyterhub jail，**一個人連續打錯密碼就會封掉整條 tunnel**，造成全體斷線。

- 處置：`ignoreip = 127.0.0.1/8 ::1`；外網側的登入防護改由 Cloudflare Access（身分驗證）＋ WAF rate limiting 承擔；fail2ban 保留給 Tailscale overlay 內的 sshd 與直連 8000 埠的來源。

### 4.2 aarch64 套件問題比預期小得多，但 pyradiomics 是硬骨頭

盤點 36 個常用套件（`linux aarch64 / cp312`）：22 個純 Python、13 個有可用 wheel（SimpleITK／ITK／OpenCV 為 `cpXY-abi3` 穩定 ABI，xgboost 為 `py3-none-aarch64`），**只有 `pyradiomics` 需要自行建置**。

`pyradiomics 3.1.0` 在 Python 3.12 完全裝不起來，且**與 CPU 架構無關**（已在 x86_64 上逐層實測）：

1. 隔離建置：`setup.py` 建置期 `import numpy` 但未宣告於 `build-system.requires` → `ModuleNotFoundError: No module named 'numpy'`
2. 關掉 isolation 並預先安裝 numpy/versioneer：vendored `versioneer.py` 呼叫 `configparser.SafeConfigParser()`，Python 3.12 已移除 → `AttributeError`
3. patch 掉 versioneer 後：`radiomics/src/_cmatrices.c:6:10: fatal error: cmatrices.h: No such file or directory`——PyPI sdist 漏包 C header

- 處置：radiomics 獨立成 `lab/radiomics-arm64`（`python:3.11` ＋ `numpy<2` ＋ `--no-build-isolation` ＋ 從 GitHub repo 安裝），不與主訓練映像混用。

## 5. 未驗證項目

沙盒沒有 GPU、Docker daemon、systemd、arm64 硬體與外部網域，因此以下項目**未經驗證**，必須在真機逐項確認（清單見 proposal §11.2）：

- Docker ＋ NVIDIA Container Toolkit 實際啟動容器、`device_requests` 是否真的把 GPU 給到容器
- MIG／vGPU 不支援與統一記憶體上限攔不住（引自 NVIDIA 官方論壇回覆，未實測）
- 兩個 arm64 映像的實際建置結果
- Tailscale 與 Cloudflare Tunnel／Access 的實連與政策生效
- disk quota（沙盒無 loop device）、`auditd` 規則

**本報告能證明的是：設定檔本身正確、權限模型如設計運作、安全機制在被誤設時會擋下來。不能證明 GPU 與外網連線在真機上可用。**
